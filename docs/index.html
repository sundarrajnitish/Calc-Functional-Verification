1 · Devices under test

Two calculators, four ports each

Both designs come from the IBM "calc" family used to teach functional verification. Four requesters share two execution units, so the interesting bugs live in the plumbing (arbitration, timing, tags, hazards), not in the arithmetic. The course supplied them as encrypted netlists that only run in Questa; this project adds open, readable reference versions with the same ports so anyone can simulate them.

Calc1: the protocol

Each port sends a command and operand 1 in one cycle and operand 2 in the next. Some cycles later the port sees exactly one response. A port may only have one command outstanding.

Generated by the JavaScript model: an ADD of 5 + 3 on port 1. The command is sampled in T0, operand 2 in T1, and the response is visible in T6.

Calc1: commands and responses

5shift leftop1 << op2[27:31] (low 5 bits)

Responses: 0 = none this cycle, 1 = success (out_data valid), 2 = overflow / underflow / invalid, 3 = unused. Bit 0 is the MSB (IBM numbering).

Calc1: inside the box

  • Input stage per port: a 4-state FSM (IDLE → OP2 → PEND → BUSY) that captures both operands.
  • Priority arbiter: each cycle, each unit takes the lowest-numbered pending port. Port 1 always wins ties.
  • ADD unit (add/sub) and SHIFT unit (shl/shr): 3-stage pipelines, one new command per cycle each.
  • Reset: reset[1:7] held to all ones for at least 7 cycles.

Calc3: registers, tags, branches

Calc3 replaces raw operands with sixteen 32-bit registers. A request carries every field in one cycle: cmd, d1, d2, r1, tag, data. A 2-bit tag lets a port keep up to four commands in flight; responses come back out of order and are matched by tag.

cmdnameeffectlatency
1addR[r1] = R[d1] + R[d2] (carry → resp 2)3
2subR[r1] = R[d1] − R[d2] (borrow → resp 2)3
5shlR[r1] = R[d1] << R[d2][27:31]4
6shrR[r1] = R[d1] >> R[d2][27:31]4
9storeR[r1] = data1
10fetchout_data = R[d1]1
12branch if zeroif R[d1] = 0, skip this port's next command1
13branch if equalif R[d1] = R[d2], skip next command1

Responses: 1 = success, 2 = overflow / underflow / invalid (destination not written), 3 = skipped by a taken branch (no effect).

The ordering rule the testbench relies on

Every command takes effect in the cycle it is accepted, in port order 1 → 4. A port-2 fetch sees a port-1 store to the same register made in the same cycle. Only the response is delayed, by 1, 3 or 4 cycles depending on the unit, so a quick fetch can overtake a slow shift on the same port.

That is why the Calc3 scoreboard keys expected results by (port, tag) and feeds the reference model from an input monitor (what the DUT actually sampled) instead of from the sequencer's intentions.

3 · Methodology

A layered, self-checking testbench

The 2024 testbenches were four copies of the same hand-written sequence, one per port, with a global cycle counter and checks by eye. The rewrite follows the standard verification architecture: every component has one job, the stimulus is constrained-random, the expected result of every transaction comes from an independent reference model, and progress is measured against a coverage plan.

Transaction & generator

A transaction is one command with its operands. The generator randomizes it under constraints that bias toward corners: zero, one, all-ones, tiny shift amounts, carries and borrows, and about 10% illegal opcodes.

constraint c_cmd { cmd dist {
  1 := 30, 2 := 30, 5 := 15, 6 := 15,
  [3:4] :/ 3, [7:15] :/ 7 }; }
constraint c_op1 { op1 dist {
  0 := 5, 32'hFFFF_FFFF := 5,
  [1:15] :/ 10,
  [16:32'hFFFF_FFFE] :/ 80 }; }

Driver & monitor

One reusable driver per port, working through clocking blocks, so drives land 1 ns after the edge and samples are taken just before it. That removes the posedge/negedge race in the old benches. The monitor watches every edge, pairs each response with the command in flight, and flags X values, spurious responses and hangs (64-cycle timeout).

vif.drv_cb.cmd[p] <= t.cmd;
vif.drv_cb.din[p] <= t.op1;
@(vif.drv_cb);
vif.drv_cb.cmd[p] <= 0;
vif.drv_cb.din[p] <= t.op2;

Reference model & scoreboard

The reference model is the spec written as a function, with no timing and nothing shared with the RTL. The scoreboard sorts every outcome into wrong_data, wrong_resp, x_on_output, no_response or spurious, so a failure report already hints at the root cause.

1: wide = {1'b0,op1} + {1'b0,op2};
   if (wide[32]) exp_resp = 2;

5 · What the 2024 campaign found

Reading root causes out of failure logs

The 2024 campaign ran on the encrypted course DUT in Questa, so there was no RTL to read, only transcripts. Mining those logs again gives a precise fault model for each failure signature. Injecting that model into the open RTL reproduces the logs exactly. Each chart below is drawn from the original log lines.

Finding 1: operand-2 bit 4 is bridged to bit 5 in the port-1 adder

!50.5% of 1,001,001 ADD checks failed

The 2024 bench swept a = 0…1000 × b = 0…1000 on port 1. The saved excerpt covers a = 997…1000. Every failing result contains an X in the second or third hex digit, and nowhere else. One rule explains every line: X appears if and only if bit 4 ≠ bit 5 of operand 2 (3,321 / 3,321 lines). With the bit-4 net fighting the bit-5 net inside a ripple-carry adder, the open RTL prints exactly the same digits as the 2024 log on all 3,321 lines.

result contained Xcorrectrows: a = 997…1000 · columns: b = 0…1000 · hover for the log line

Why a stripe every 64 values?

Bits 4 and 5 of b repeat with period 64: 00, 01, 10, 11 in runs of 16. X happens on the two middle runs (01 and 10), so b = 16…47 fails, 48…79 passes, 80…111 fails, and so on: 32 failing values, then 32 passing ones. Drag the slider to see the fault travel through the adder.

Findings 3 & 4: shifts by 0 and 1

SHL by 0 gave X for every non-zero operand (0 << 0 still read 0). SHR by 0 gave 0, and SHR by 1 returned the operand unshifted. All other amounts were correct: 60 failures in 1,344 checks, all in columns 0 and 1. Replaying the sweep on the open RTL with bugs 3 and 4 gives the same 1,344 results.

Finding 5: the 2024 Calc3 scoreboard was the loudest source of errors

The Calc3 environment reported 4,442 matches and 1,408 mismatches. Replaying its logic line by line shows that most mismatches came from the checker, not the DUT:

  • On every DUT response it compared all four ports, so ports that had not answered re-matched a stale value (703) and inflated the "correct" count (500 stale matches in the saved excerpt alone).
  • The reference model was loaded with ports[i-1], off by one and out of range for i = 0, and then re-executed the last command of all four ports on each check.
  • Responses were matched by port only, never by tag, so every legal out-of-order response became a "tag mismatch", which is the largest bar on the right.

The rewrite fixes all three: an input monitor feeds the predictor, expected results are keyed by (port, tag), and only the responding port is checked.

Mismatch kinds in the saved 2024 log excerpt (132 mismatches).

Verifying the verifier: bugs in the 2024 testbenches

A testbench is code too, and it had bugs. These are the ones that changed the verdicts, with the fix in the rewrite.

Response 2 treated as “no response” 
while (out_resp1 !== 2'b01) begin   // 2024
  @(negedge c_clk);
  if (clk_count >= 50 ...) break;
if (r !== RSP_NONE) finish_txn(p, r, d);   // 2026
// resp 2 is a legal answer: checked against
// the reference model like any other

Overflow, underflow and invalid-command responses were counted as hangs. That is where the "No Response: 120" in the SUB log comes from.

A global cycle counter that never resets

clk_count counted from time 0 and the wait loops broke out once it passed 50 (or 100). After the first ~50 cycles every later wait returned at once, so later operations were "checked" before their response existed. The rewrite uses a per-transaction timeout measured from its own issue cycle.

Race between stimulus and DUT sampling

Commands were written with blocking assignments right after @(posedge c_clk), the same edge on which the DUT samples, and operand 2 half a cycle later. Which value the DUT sees depends on scheduling order. The rewrite drives through clocking blocks (output #1) and samples with input #1step.

Four copies of every test, and messages that lie

Each scenario was pasted four times (one per port), and the NO-OP check printed "successful" in the failure branch and "failed" in the success branch. The rewrite has one parameterized driver per port and a scoreboard that prints the expected and the actual values.

Calc3: scan clocks driven with the functional clock

a_clk and b_clk are the LSSD scan clocks. The test toggled them together with c_clk, which puts a real LSSD design into scan-shift mode. They are now held low.

Coverage that measured the stimulus, not the plan

The 2024 covergroup sampled input fields (tags, register indices) on every negedge, including idle cycles, and had no coverpoint for the command itself. The new model counts plan items: command × port, every shift amount, carries and borrows per port, walking ones, taken and not-taken branches, skipped-command kinds, outstanding depth, out-of-order responses and hazards.

6 · Regression results

Every bug caught, no false alarms

The SystemVerilog environments were compiled with Verilator 5.052 (classes, mailboxes, constrained randomization through an SMT solver) once per design variant. The golden design has to pass and every injected bug has to fail. Seeds 1–3 are shown; the “first failure” column is the scoreboard’s own message.

Replaying 2024 on the open RTL

sim/check_replay.py re-runs the 2024 port-1 sweeps on Icarus Verilog (4-state, like Questa) and diffs every result line against the old logs.

JavaScript ≡ RTL

sim/check_js_models.py drives random stimulus, including protocol violations, into the Verilog and into this page’s models, and compares all outputs on every cycle, for every bug.

Where the time goes

Each SV regression run takes one to two minutes, mostly spent in the SMT solver behind randomize(). The same tests in this page’s JavaScript bench run in well under a second.

7 · Reproduce it

Run everything locally

  1. Tools: Verilator ≥ 5.036 with z3 (the constrained-random TB), Icarus Verilog 12 (4-state replay and trace checks), Python 3, Node 18+.
  2. Build all 16 variants: sim/build.sh
  3. Regress: python3 sim/regress.py --seeds 1,2,3 --jobs 4
  4. Replay 2024: python3 sim/check_replay.py
  5. Check the web models: python3 sim/check_js_models.py
  6. Re-mine the logs: python3 analysis/analyze_2024_logs.py
